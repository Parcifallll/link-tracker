# Отчет о соответствии приложения 12 факторам (12/12)

## 1. Codebase
- Один репозиторий в VCS (Maven multi-module: `bot`, `scrapper`).
- Все окружения запускаются из одного кода, различие задаётся профилем `SPRING_PROFILES_ACTIVE` (`dev`, `prod`).

## 2 - Dependencies
Все зависимости объявлены явно и изолированы через pom.xml.

## 3 - Config
- Конфигурация хранится в окружении application.yaml (порты, адреса сервисов, токены, интервалы).
- Секреты хранятся в `.env`, в репозитории только `.env.example` без значений.
- Код не содержит конфигурацию.

## 4 - Backing services
- PostgreSQL, Kafka, Valkey и внешние API подключаются как ресурсы по адресам из переменных окружения.
- Сервисы заменяются через конфигурацию не через код.

## 5 - Build, release, run
- Build: `mvn package` даёт jar; release: `docker build` собирает образ с версией артефакта (`0.0.1`).
- Run: `docker compose up` запускает образы с конфигом из окружения, без пересборки.

## Processes
- Приложение запускается как процесс без состояния
- Состояние вынесено во внешние сервисы: подписки в PostgreSQL, кэш в Valkey, сообщения в Kafka.
- Приложение переносится между машинами и не привязано к конкретному железу и ОС

## Port binding
- Сервисы экспортируются через привязку портов.
- Сервисы доступны друг другу по сети.

## Concurrency
- Масштабирование за счёт добавления процессов: экземпляры `bot` делят сообщения Kafka через общий `KAFKA_CONSUMER_GROUP`.

## Disposability
- Приложение корректно завершается (`server.shutdown: graceful`, таймаут 30s)
- Данные восстаналиваются из хранилищей после перезапуска (без потери данных при завершении).

## Dev/prod parity
- Профили `dev` и `prod` отличаются только уровнями логирования.
- В обоих окружениях одинаковый стек и общий `application.yaml`.

## Logs
- Логи пишутся в stdout в структурированном формате ECS.
- Приложение не управляет файлами логов, сбор остаётся за окружением.

## 12 - Admin processes
- Миграции БД выполняет одноразовый контейнер Liquibase, он завершается до старта приложений.
